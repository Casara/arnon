# Using arnon

`arnon` is a minimalist Go HTTP foundation: typed endpoints, automatic
request binding/sanitization/validation, RFC 9457 (Problem Details)
errors, and OpenAPI 3.2 generated by reflection. This skill is for code
that *consumes* arnon as a dependency, not for arnon's own source - if
you're working inside the `arnon` repo itself, follow its `CLAUDE.md`
instead.

## Typed endpoints

A handler is a plain function, never `http.HandlerFunc` directly:

```go
func createUser(ctx context.Context, req CreateUserRequest) (CreateUserResponse, error)
```

Wrap it with `httpx.Endpoint(handler, httpx.EndpointConfig{...})` and
register the result on a `*routing.Router`/`*routing.Group` like any
other handler (`router.POST("/users", httpx.Endpoint(...))`).
`EndpointConfig` fields are all optional (`WithDefaults()` fills
`Validator`, `ProblemMapper`, `SuccessStatus` - never nil-check these
yourself downstream, they're always non-nil after construction):

* `SuccessStatus` - HTTP status for the success path (default 200).
* `Validator` - override the validator instance; almost never needed.
* `ProblemMapper` - a `func(error) *problem.Problem` (wrap with
  `httpx.ProblemMapperFunc`) to map handler errors to specific Problem
  Details instead of the generic 500 fallback.
* `OpenAPI` - **opt-in**. A route only appears in the generated OpenAPI
  document if this is set, even to an empty `&openapi.Operation{}`.

`httpx.Endpoint` is JSON-only by design (it's the point: one typed
schema, request and response). For XML, PDF, file downloads, or any
other non-JSON response, don't look for a typed-endpoint equivalent -
mount a plain `http.Handler` directly on the router
(`router.GET("/report.pdf", myHandler)`). No middleware in arnon is
coupled to JSON, so this works with the same middleware stack. See
`examples/cmd/files` for a runnable download/upload example (PDF, CSV,
XML).

`ETag`/`Compress` are both safe to put in front of a Range-capable
handler (`http.FileServer`, `http.ServeContent`, static assets, resumable
downloads, media seeking): both step aside for any request carrying a
`Range` header, so the underlying handler's own Range/`If-Range` support
runs untouched - see the doc comments on
`middleware.ETag`/`middleware.Compress` and `examples/cmd/staticfiles`
for the confirmed-empirically detail. No special scoping needed for
this specific concern; `Group.Use` is still how you'd scope either for
unrelated reasons, same technique as `examples/cmd/middleware`'s
`AllowContentType`/`MaxBodyBytes`.

## Request binding

Struct tags select the source per field: `json` (body), `path`,
`query`, `header`. A field can only use one source.

```go
type GetUserRequest struct {
    ID     string   `path:"id"`
    Tags   []string `query:"tags"`
    Locale []string `header:"Accept-Language"`
}
```

`[]string` fields behave differently depending on the source - this is
deliberate, not an inconsistency:

* **header**: repeated header lines *and* a single comma-separated
  line are both collected into the slice (RFC 9110 §5.3 treats them as
  equivalent for headers).
* **query**: only repeated keys are collected (`?tag=a&tag=b`) - a
  single value is **never** split on commas, since there's no RFC
  defining that for query strings and it would break a legitimate
  value like `?q=cats,dogs`.

## Sanitization

`sanitize` struct tags transform a field's value between binding and
validation, so `required`/`min`/etc. see the value the client intends,
not raw bytes that happen to satisfy the check without meaning to:

```go
type CreateUserRequest struct {
    Email string `json:"email" validate:"required,email" sanitize:"email"`
}
```

Built-in: `trim` (`strings.TrimSpace`) and `email` (trim + lowercase) -
deliberately minimal, register anything else
(`sanitize.RegisterFunc("digitsOnly", fn)`) the same way as a custom
validation rule, at bootstrap. A struct field is always recursed into;
a slice/array/map field needs its tag to start with `dive`
(`sanitize:"dive,trim"` on a `[]string`), matching `validate`'s own
convention. Scoped to `string` fields only.

## Validation

Tags follow `go-playground/validator/v10` syntax
(`validate:"required,email"`). Two gotchas worth knowing before writing
a request struct:

* **`min`/`max` are length constraints, not numeric bounds.**
  `validate:"min=1,max=100"` on an `int` is almost always a mistake -
  it means "1 to 100 characters" if the field were a string, not "1 to
  100 in value". For numeric ranges use `gt`/`gte`/`lt`/`lte`.
* **`required` rejects zero values, not whitespace-only strings.**
  `"   "` passes `required` (it's non-empty). Add `sanitize:"trim"` to
  the same field and `required` alone is enough (whitespace-only
  becomes `""`, the actual zero value) - reach for a custom validation
  rule only if trimming isn't the right fix for that field.

Custom validation tags are registered **once**, at application
bootstrap, via `validation.RegisterCustomRule` - never configure a
`*validator.Validate` instance directly, or the tag won't be picked up
by OpenAPI generation:

```go
validation.RegisterCustomRule(validation.CustomRule{
    Tag:  "notblank",
    Func: validateNotBlank,
    Code: "blank",
    Message: func(param string) string { return "must not be blank" },
    Schema: &validation.SchemaEffect{Pattern: `\S`},
})
```

One registration feeds runtime validation, the RFC 9457 error mapping
(`code`/`detail`), and the generated OpenAPI schema at the same time -
there's no separate step for any of the three.

## Errors and Problem Details

Handlers return a plain `error`. arnon maps it to a `problem.Problem`
(RFC 9457, `application/problem+json`) automatically - don't call
`http.Error` or write JSON error bodies by hand inside a handler
wrapped by `httpx.Endpoint`. To control the mapping for a specific
error type, pass a custom `ProblemMapper` in `EndpointConfig`; anything
unmapped falls back to a generic `500`.

## Router and middleware

```go
router := routing.NewRouter(routing.WithOpenAPI(openapi.NewRegistry(generator)))
router.Use(middleware.BuildChain(middleware.ChainConfig{
    Recover:   true,
    RequestID: true,
    // ...
})...)
```

Prefer `middleware.BuildChain` over hand-listing
`router.Use(mw1, mw2, ...)`: it always assembles the recommended global
middleware in the same relative order (`Recover` outermost, `RequestID`
before `Logging`, `ETag` before `Compress`, etc.), so enabling or
disabling an entry in `ChainConfig` can't silently break that order.
If a hand-written or third-party middleware has an ordering requirement
against a built-in one (e.g. "must run right after `RateLimit`, before
`ETag`"), anchor it via `ChainConfig.Extra`:

```go
Extra: []middleware.ExtraMiddleware{
    {Middleware: myMiddleware(), Before: middleware.AnchorETag},
},
```

`router.Use(...)` (global) wraps the whole `net/http.ServeMux`,
including unmatched routes - a global `Recover`/`RequestID` also
applies to 404s. `group.Use(...)` (`router.Group("/api")`) is per-route
instead, since `ServeMux` has no native notion of a path prefix; scope
middleware there when it should only apply to a subset of routes (e.g.
`AllowContentType`, `MaxBodyBytes` on a JSON-body group, not on
`/openapi.json`/`/docs`).
